# Объекты, переходы и доказательства

Реализованный локальный этап SHAIM, 31 октября 2026, Europe/Moscow.
Этот документ описывает текущий код. Запуск окружения — в [README](README.md),
математические ограничения — в [RESEARCH_METHOD](RESEARCH_METHOD.md).

## Три представления

| Представление | Узлы и связи | Что из него следует |
|---|---|---|
| MSC2020 | Рубрики, иерархия и официальные отсылки | Тематика и навигация |
| Объекты и переходы | Определения, параметры, условия; конструкции, представления, переносы свойств, эквивалентности и сведения | Конкретные предложенные отношения с проверяемыми контрактами |
| Доказательство | Обязательные цели, вспомогательные леммы и зависимости | План доказательства либо зависимости уже скомпилированных деклараций |

Расстояние на MSC-карте не является математическим сходством. Использование
определения в доказательстве не является отображлением между объектами.
Граф объектов допускает циклы; план доказательства проходит проверку ацикличности.

Переход может иметь несколько исходных и целевых объектов. В интерфейсе он
показан отдельным узлом между ними, чтобы его условия и обязательства можно
было выбрать однозначно. Например, тождество энергии треугольника и квадратичной
формы и перенос неотрицательности — два отдельных перехода. Второй требует
знаковых условий; первый верен и при отрицательных весах.

## Пользовательский сценарий

В основном каталоге ровно два примера: `arxiv_2610_38474_graph_subtraction`
(полиномиальный шаг §9.1 статьи Frolov/Dorofeev) и `published_associator_laplacian`
(наша опубликованная связь ассоциатора и графового лапласиана). Остальные фикстуры
сохраняются как внутренние контрольные задачи.

1. На карте MSC выберите область и нажмите «Исследовать» либо откройте лабораторию.
2. «Проверить связь» позволяет выбрать подготовленный пример или свой вопрос.
   «Предложить связи» создаёт до трёх гипотез по вопросу и MSC-области; это отдельный
   модельный запуск без проверки доказательств. Для импортированной статьи
   серверный предел — шесть переходов.
3. В «Объекты и переходы» выберите объект для просмотра определения и условий,
   затем переход для просмотра конструкции, утверждения, источников и всех целей.
4. «Проверить выбранный переход» создаёт запуск для точной версии графа. Для
   подготовленного неизменённого перехода доступен локальный пилот; остальные
   переходы используют Astra с указанным бюджетом.
5. «Открыть граф лемм» или кнопка конкретного обязательства переводит в представление
   «Доказательство». Статус другого перехода не переносится на выбранный;
   для ещё не проверенного перехода может быть показан только план.
6. «Уточнить постановку» открывает редактор описаний, условий и формальных типов.
   Сохранение создаёт новую версию, а не меняет старое доказательство. Русское
   описание и Lean-тип редактируются явно; кнопка «Новый вопрос для Astra» переносит
   текст в новую постановку, когда нужна новая формализация.

Сохранённые графы доступны в списке «Графы объектов». У графа есть переключатель
версии; UI показывает до 30 последних версий и текущую открытую историческую.
API позволяет получить любую существующую версию. «Результат», «Ход работы»,
«Источники и поиск» сохраняют доступ к исходникам, проверкам и попыткам.

Редактор сохраняет новую версию только для уже сохранённого графа. Предпросмотр
готового примера получает граф в реестре при первом запуске. Изменение его
математического содержания запрещает использовать прежний локальный пилот
как доказательство новой постановки.
Редактор уточняет существующие объекты и переходы; добавление и удаление узлов
не представлены как операции визуального конструктора. Новую структуру можно
получить отдельным предложением Astra; API версии принимает полный граф.

Для статьи используйте блок «Источник arXiv»: явная ссылка → «Импортировать
статью» → сохранённая версия → раздел → «Выделить объекты и переходы».
Последняя кнопка только готовит вопрос; отдельный запуск извлечения вызывает Astra.
Карточка результата имеет метку «Утверждение статьи» и действие
«Формализовать и проверить». До получения точных Lean-целей граф лемм для неё
не показывается как доказательство. Импорт и просмотр статьи модель не вызывают.

## Компоненты и процесс

| Компонент | Ответственность |
|---|---|
| `research_objects.py` | Валидация предметных графов, SQLite-версии, хеши и привязки результатов |
| `research_object_examples.py`, `research_arxiv_example.py`, `research_published_example.py` | Графы двух основных примеров и внутренних контролей |
| `research_project_library.py` | Свежая сборка нужных модулей MathResearch в каталоге запуска с хешами исходников и `.olean` |
| `research_arxiv.py` | Явный импорт версии arXiv, HTML/MathML, снимки и локальный поиск по фрагментам |
| `research_transition_schema.py` | Структурированный ответ Astra для предложения объектов и переходов |
| `research_service.py` | Бюджет, роли, неизменные контракты, LangGraph, публикация результатов |
| `research_codex.py` | App Server по stdio, точная модель, попытки, отмена и восстановление |
| `research_lean.py` | Компиляция, аудит, проверка основной цели и всех обязательств |
| `web/object-graph.js`, `web/research.js` | Связанные представления, инспектор, редактор и выбор версии |

LangGraph использует этапы:

```text
retrieve → propose_transitions → formalize_transition → validate_contract → investigate → certify_transition → publish
```

Это граф исполнения с SQLite checkpoints. Математический DAG лемм находится
внутри `investigate`: план → критика → доказательство доступных узлов →
пересмотр при допустимой неудаче → итоговая композиция → проверка смысла.
Goedel-Architect служит источником подхода к декомпозиции; готовый движок
Goedel-Architect не импортирован, его результаты не приписываются SHAIM.

Для `purpose=discover` после предложения сохраняется граф гипотез; стадии
доказательства пропускаются. Контроллер сохраняет исходный вопрос и MSC-метки,
не принимает подменённую моделью формулировку вопроса. Ссылки в предложении
должны ссылаться на найденные evidence IDs; название, URL и локатор восстанавливаются
из этих материалов. Предложенные объекты всё ещё требуют содержательной оценки.

Для `purpose=prove` проверяется один выбранный переход. Перед доказательством
новая формализация проходит отдельную модельную проверку; при `mismatch` или
`uncertain` запуск сохраняет `unknown` и требует новой постановки. Проверенный
пилот использует заранее описанную содержательную оценку.

Для литературного перехода `formalize_transition` создаёт отдельный производный
граф с точным контрактом. Ссылки `source_graph_ref`, `source_transition_id` и хеш
исходного перехода сохраняются в запуске/его контракте; исходная версия не
переписывается. Ответ `needs_review` завершает запуск с `unknown`, без доказательства.
Сохранённый ответ формализатора и идемпотентный ключ создания позволяют продолжить
после сбоя до привязки нового графа без повторного запроса модели или дубля графа.

При ошибке Lean можно исправить доказательство узла и один раз пересмотреть
недоказанную часть плана. Контракт перехода, определения и подтверждённые леммы
сохраняются. Изменение обязательного типа или предпосылок — новая версия графа
и новый запуск. Тайм-аут и исчерпание бюджета означают `unknown`, а не опровержение.
Перед второй попыткой доказать узел контроллер выполняет дополнительный локальный
поиск по его типу и диагностике Lean. До шести результатов, запрос и манифест корпуса
сохраняются в `retrieval/vN-<node_id>.json`; продолжение использует этот файл.

## Снимок статьи и область источников

`ArxivLibrary(root)` предоставляет `import_paper(reference)`, `list_papers()`,
`get_paper(versioned_id)`, `search(query, paper_ids, limit=6)` и
`evidence(paper_id, section_ids=None, limit=12, max_chars=24000)`.
Сеть используется только в явном импорте. Зафиксированная версия повторно
читается из кэша; локальный поиск не обращается к arXiv. Если полноценный HTML
недоступен, импорт возвращает ошибку без подстановки аннотации или PDF/OCR.

В `research_data/arxiv/<version>/` сохраняются `abstract.html`, `article.html`,
`chunks.json` и `paper.json`. Метаданные содержат `versioned_id`, `title`, `authors`,
`msc_codes`, `abstract`, канонические `source_urls`, `fetched_at`, `snapshot_sha256`,
`math_extraction`, `limitations` и `sections`. У раздела есть ID, заголовок, ссылка,
абзацы, уравнения с метками/LaTeX и список chunk IDs. MathML `alttext` или TeX-аннотация
сохраняет формулу без OCR; отсутствие TeX отражается в ограничениях.

Evidence record содержит точный нормализованный `text/content`, `id`,
`versioned_id`, `section_id`, URL раздела, SHA текста и SHA исходного HTML.
Фрагменты не являются проверенными декларациями. Контракт исследования фиксирует
версии, разделы и хеши снимков. `source-evidence.json` и `source_scope` описывают
фактически переданный контекст: запрошенные/переданные разделы, число фрагментов
и `complete_selected_scope`. Для статьи выбираются не более 16 целых фрагментов;
28 000 символов распределяются между выбранными статьями. Поэтому «вся статья»
в интерфейсе означает область отбора, а не гарантию передачи полного текста модели.

На arXiv:2610.38474v1 подготовлен переход `graph_subtraction` из
[§9.1](https://arxiv.org/html/2610.38474v1#S9.SS1): уже полученный полиномиальный
граф `(b(t),t,w(t))` переводится в координатную ось. Три обязательства проверяют
обе композиции `S=(y,x−b(y),z−w(y))`, `S⁻¹=(X+b(T),T,Z+w(T))` и образ графа
как равенства полиномов. Предшествующее приведение произвольной кривой к графу,
выпрямители узлов и мотивные результаты статьи в контракт не включены.

Второй основной пример, `published_associator_laplacian`, берётся из нашего
препринта v1.5 и модуля `MathResearch.AlbertSpectralGeometry`. Объекты
`AlgebraObject.energy` и `GraphObject.energy` связаны `Bridge.energy_correspondence`,
который использует опубликованную теорему `associatorDirichlet_graphLaplacian`.
Область — рациональная координатная модель и трёхвершинная энергия с весами
`(dᵢ−dⱼ)²/4`. Это воспроизведение существующего результата. Зависимости
`MinimalAInfinity`, `AlbertObstruction`, `AlbertMatrix`, `AlbertSpectralGeometry`
компилируются заново для проверки; состав и хеши записываются в `project-library.json`.

## Формат предметного графа

Входной граф содержит следующие поля. Известные вычисленные поля из `get()`
отбрасываются при сохранении новой версии; переданный клиентом статус или
сертификат не создаёт свидетельства проверки.

| Сущность | Поля |
|---|---|
| Граф | `title`, `question`, `msc_codes`, `objects`, `transitions`, `sources`; необязательный `layout` |
| Объект | `id`, `title`, `kind`, `definition`, `parameters[]`, `assumptions[]`, `msc_codes[]`, `lean_refs[]` |
| Переход | `id`, `title`, `source_ids[]`, `target_ids[]`, `relation_type`, `construction`, `assumptions[]`, `claim`, `obligations[]`, `agent_task`, `case_id`; необязательные `formulation_status`, `source_refs[]` |
| Обязательство | `id`, `title`, `target`, `statement`, `expected_outcome` |
| Формальная задача | `imports[]`, `prelude`, `target`, `statement` |
| Источник | `id`, `title`, `url`, `locator`; необязательные `versioned_id`, `snapshot_sha256`, `section_id` |

`relation_type` принимает `construction`, `representation`, `property_transfer`,
`equivalence` или `reduction`. `expected_outcome` — `proved` либо `refuted`;
последний означает смысл проверяемой отрицательной цели, а не сообщение о
неудаче доказателя. `case_id` у нового предложения равен `null`.

ID графов, запусков и публикаций — UUID в виде 32 шестнадцатеричных символов.
Локальные ID объектов, переходов и обязательств — устойчивые безопасные строковые
ключи, отдельные от полных Lean-имён в `target`. Ссылки на объекты должны существовать,
ID внутри соответствующих списков должны быть уникальны. У формализованного перехода
обязателен непустой список целей; основная пара `target/statement` должна точно
совпадать с одним из обязательств. MSC-коды сверяются с локальным классификатором.

`formulation_status` равен `formalized` по умолчанию для старых графов.
Для `literature_only` допустимы только `agent_task=null`, `obligations=[]`,
`case_id=null`; попытка записать «успешный» отчёт не создаёт сертификат.
`source_refs` ссылается на существующие ID в `sources`. В предложении по статье
каждый переход обязан цитировать переданный фрагмент arXiv. Контроллер восстанавливает
URL, локатор, версию и хеш цитаты; не доверяет придуманным моделью реквизитам.
Отсутствующие необязательные поля не добавляются в старые payload, сохраняя
их хеши и идемпотентность.

Описания объектов — предметные данные, а не автоматически проверенные Lean-типы.
`prelude` хранит определения; обязательства содержат полные типы с кванторами
и предпосылками. Их соответствие описанию оценивается отдельно. Реестр не выводит
законы сохранения из слова «эквивалентность»: обязательства нужно явно задать.

## Несколько обязательств и сертификат

Планировщик получает `required_obligations` выбранного перехода. Каждая цель
обязана присутствовать в плане с тем же полным именем и типом, даже если
вспомогательный результат не используется в доказательстве основной теоремы.
Финальная композиция содержит все полученные теоремы. Один модуль `Contract.lean`
проверяет основную цель и каждое обязательство через независимые проверки типов.

Для сертификата registry требует одновременно:

- `success`, `compilation_success`, `target_preserved`, `obligations_passed` равны `true`;
- аудит аксиом имеет `status=passed`, нет неожиданных аксиом или unsafe-деклараций;
- итоговые `target` и `expected_statement` совпадают с контрактом;
- список `verification.obligations` содержит ровно ожидаемые ID, полные имена,
  SHA-256 текста каждого типа и `ok=true`;
- итог соответствует `expected_outcome` основной цели, зафиксирован fingerprint окружения.

Результат передаёт внутренний контроллер, не браузер. Он имеет форму:

```text
{
  publication_id, formal_outcome, semantic_review, environment_fingerprint,
  verification: {
    success, compilation_success, target_preserved, audit,
    target, expected_statement, obligations_passed,
    obligations: [{id, target, statement_sha256, ok, ...}], ...
  }, ...
}
```

Сам HTTP API не предоставляет метод загрузки «успешного сертификата» от клиента.
Формальный результат не подтверждает новизну, полезность или автоматически
полноту выбранной математической модели.

## Версии, публикации и статусы

`GraphRegistry` хранит данные в `research_data/objects.sqlite`. Версии графа
неизменяемы. `revise` требует `expected_revision`, чтобы параллельные изменения
не перезаписывали друг друга. Методы библиотеки: `create`, `get`, `list_graphs`,
`revise`, `record_result`; экспортированы `validate_graph`, `transition_contract`,
`graph_fingerprints`, `transition_fingerprint`.

Каждый результат связан с точными `(graph_id, revision, transition_id, run_id,
publication_id)`. Повторная доставка той же публикации с тем же payload
идемпотентна; изменение payload запрещено. Продолжение одного запуска может
добавить новую публикацию. Частичные и неудачные публикации остаются в истории.
Сохранённый `transition-result-<publication_id>.json` позволяет восстановить
результат после сбоя между файловой и SQLite-записью. Идемпотентное создание
графа защищает от дубля при сбое до привязки графа к запуску.

Хеш `semantic_hash` вычисляется из выбранных полей постановки; это не алгоритм
математической эквивалентности формулировок. Определения, параметры, предпосылки,
конструкция, утверждение, формальные задачи и вопрос влияют на хеш. Названия,
MSC-метки, расположение узлов и названия библиографических записей не меняют его.
При наличии `source_refs` в привязку входят также URL, локатор, версия и хеш
указанных источников. Смена цитируемого снимка не считается косметической правкой.

Перенос сертификата в новую версию допускается только при совпадении хеша
перехода и явно известного окружения. Окружение учитывает выбранный компилятор,
toolchain, manifest и ревизию mathlib. При смене активного окружения старое
свидетельство остаётся историческим; для текущего статуса нужна новая проверка.
Поздний результат старой версии не обновляет новую версию, даже если они
содержат одинаковые тексты. Повторно неудачная попытка той же постановки не
удаляет уже проверенный сертификат: `certificate` и `last_result` различаются.

| Статус перехода | Значение |
|---|---|
| `proposed` | Сохранён переход без результата проверки; литературная карточка ещё не имеет Lean-контракта |
| `proved` | Все обязательные цели подтверждены для точного контракта и окружения |
| `refuted` | Подтверждена предусмотренная контрактом отрицательная основная цель |
| `unknown` | Попытки есть, достаточного сертификата нет |
| `needs_recheck` | Есть историческое свидетельство, которое не подходит к версии или окружению |

В UI `proposed` отображается как «Гипотеза», а для `literature_only` — как
«Утверждение статьи»; `unknown`/`needs_recheck` — как
«Неполно» с пояснением. `semantic_review` показывается отдельно от Lean-статуса.
В агентном запуске общий `outcome` остаётся `unknown`, пока оценка смысла
не вернёт `aligned`, даже при наличии формального результата `formal_outcome`.
Завершённый `discover` — завершение генерации гипотез, а не доказательство.

## HTTP API

Сервер слушает `127.0.0.1`; POST принимает JSON от локального приложения.
Старые методы сохранённого прототипа остаются отдельными и не описывают новый UI.

| Метод и путь | Назначение |
|---|---|
| `GET /api/research/status` | Готовность процесса, Codex и точной модели; не выполняет генерацию |
| `GET /api/research/cases` | Пилоты и их предварительные `object_graph` |
| `GET /api/research/search?q=...` | Поиск по локальным карточкам и библиотечному индексу |
| `POST /api/arxiv/import` | `{reference}`; импорт явной статьи без вызова модели |
| `GET /api/arxiv/papers` | Список локально импортированных версий |
| `GET /api/arxiv/papers/{versioned_id}` | Метаданные и разделы сохранённого снимка; ID кодируется как компонент URL |
| `GET /api/research/runs` | Список сохранённых запусков |
| `GET /api/objects/graphs` | Краткий список текущих версий сохранённых графов |
| `GET /api/objects/graphs/{id}?revision=N` | Точная версия; без `revision` — текущая |
| `POST /api/objects/graphs/{id}/revisions` | `{graph, expected_revision}`; создаёт новую версию |
| `POST /api/research/runs` | Новый discovery или проверка; возвращает запуск |
| `GET /api/research/runs/{id}` | Запуск с графом той версии, которую он проверяет |
| `POST /api/research/runs/{id}/cancel` | Сохранённый запрос остановки |
| `POST /api/research/runs/{id}/resume` | Продолжение в пределах оставшегося бюджета |
| `GET /api/research/runs/{id}/artifacts/{path}` | Исходник, журнал или отчёт этого запуска |

Для discovery передаются `purpose="discover"`, `question`, `msc_codes`,
`mode="single"` или `"multi"`, `budget={max_calls, timeout_seconds}`.
Для выбранного перехода передаются `purpose="prove"`, `graph_id`,
целочисленный `graph_revision`, `transition_id`, `mode` и `budget`.
Для первого запуска готового примера достаточно `case_id`; необязательный
`transition_id` выбирает конкретный переход этого пилота. Данные `case_id`
не позволяют обойти проверку совпадения канонической постановки.
Для статьи дополнительно передаются `paper_ids:["2610.38474v1"]` и
`section_ids:["S9.SS1"]`. Пустой список разделов выбирает область всей статьи
с теми же ограничениями объёма. Сервер принимает до трёх статей и двенадцати
ID разделов; непустой выбор должен находить хотя бы один раздел в каждой статье.
При проверке сохранённого перехода источники также выводятся из его `source_refs`,
а хеши цитат сверяются с импортированными снимками.

## Границы этапа

- Корпус включает локальные карточки, библиотечный текстовый индекс и явно
  импортированные HTML-статьи arXiv. Глобальный поиск arXiv, автоматический обход
  ссылок, внешние базы, embeddings и поиск по полным elaborated Lean-типам не подключены.
- Обычный discovery ограничен тремя переходами и восемью объектами, по статье —
  шестью переходами и двенадцатью объектами. Это не обход всей математики,
  не автоматическая формализация всей статьи и не оценка научной новизны.
- Вызовы модели ограничены числом и общим временем; независимые леммы выполняются
  максимум по две. Жёсткого лимита токенов нет. Неизвестный исход внешнего вызова
  не приводит к автоматической повторной отправке.
- Дополнительный поиск после ошибки Lean ограничен локальным корпусом и второй
  попыткой доказать узел. Он не заменяет обязательный тип и не запускает
  неограниченный цикл поиска; выборка сохраняется для каждой версии плана и узла.
- Доказанные леммы повторно используются внутри проверяемого плана. Общий поиск
  переносимых лемм между разными исследованиями и автоматическая композиция
  произвольного пути из нескольких предметных переходов ещё не реализованы.
- Реестр хранит пользовательские/модельные определения, но не канонизирует
  математически эквивалентные объекты и не извлекает автоматически все законы структуры.

## Проверка реализации

`tests/test_research_objects.py` проверяет версии, конкурентное идемпотентное
создание, привязку каждого обязательства, смену окружения, поздние результаты,
историю публикаций и совместимость подготовленных контрактов. Интеграционные
проверки находятся в `tests/test_transition_workflow.py`, Lean-проверки — в
`tests/test_object_transition_lean.py`, модель интерфейса — в
`tests/test_object_graph.cjs`.
`tests/test_research_arxiv.py` проверяет импорт, версии, ограничения загрузки,
формулы и локальный поиск; `tests/test_arxiv_workflow.py` — область источников,
литературные карточки, производную формализацию и восстановление без повторного вызова.

Свежий сводный результат сохраняется в `verification/object-graph-summary.json`.
Здесь намеренно не зафиксировано ожидаемое число успешных проверок. Отчёты
`checks/` и прежние локальные отчёты подтверждают только указанные в них этапы.
Переносимые результаты текущего выпуска — [release-summary.json](checks/release-summary.json)
и [arxiv-study.json](checks/arxiv-study.json). Новая проверка создаёт собственные
локальные отчёты и не использует прежний сертификат как доказательство успеха.
