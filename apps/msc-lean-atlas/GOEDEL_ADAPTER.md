# Goedel-Architect в AMR

`goedel-adapted` — производная интеграция реального ядра
[Goedel-Architect](https://github.com/goedelarchitect/goedel-architect),
закреплённого на коммите `300d69e97c91a2a498091c898e736af69f391960`.
Это не неизменённый upstream CLI. До живого запуска с моделью статус проверки —
совместимость ядра и Lean; не подтверждение качества автономного поиска.

## Что фактически используется

`tools/goedel/upstream_core.py` содержит извлечённые upstream-функции:

- `validate_blueprint_graph` — проверка графа, циклов и достижимости;
- `graft_proof_body` — привязка доказательства к канонической сигнатуре;
- `analyze_blueprint_from_trace` — зависимости, достижимость и сохранённые узлы;
- `classify_axioms` — дополнительная классификация аксиом.

Рядом находятся Apache-2.0 `LICENSE`, `NOTICE` и `upstream-manifest.json` с
исходными файлами, строками, хешами выбранных символов и хешем включённого кода.
При старте проверяются фактические хеши. В каждой попытке сохраняется
`proof-backend.json`; смена ядра или адаптера требует новой попытки.

Два изменения upstream-кода перечислены в manifest: анализ принимает записи
узлов напрямую, а классификатор не допускает расширение разрешённых аксиом
через переменную окружения. Остальные выбранные функции сохранены буквально.

## Адаптация к правилам проекта

Штатный Goedel использует LeanArchitect и промежуточные Lean-заглушки.
AMR хранит blueprint как JSON с полными типами и зависимостями. Синтетический
корень обязательств — только запись графа, не Lean-декларация. Независимые
обязательные цели сохраняются даже вне пути к основной цели.

В Lean отправляются только определения и полные доказательства. Рабочий узел
получает настоящие проверенные доказательства родителей. Готовые независимые
узлы выполняются максимум по два одновременно. Разрешены один пересмотр по
критике и один по реальным ошибкам Lean, до двух доказательных попыток на узел.
Доказанные типы, зависимости, определения и исходная цель сохраняются точно.
Ошибка доказательства не является опровержением утверждения.

Используются закреплённые Lean 4.19.0 и mathlib проекта; Kimina, LeanArchitect
и миграция исходного математического комплекта не требуются. Промежуточные
заглушки и дополнительные аксиомы не создаются и не исполняются.

## Интерфейс контроллера

`research_goedel.run_workflow(service, run_id)` выполняет blueprint → prove →
refine, затем вызывает общий `service._finish_model_workflow(...)`. Последний
повторно компилирует итоговый исходник, проверяет точные типы **всех** обязательств,
аудит зависимостей и запускает отдельную смысловую рецензию.

Все запросы модели проходят через `service._call`: роли `plan`, `critic`,
`prove`, `revise` используют те же схемы, модель и общие лимиты. Ключи вызовов
сохраняются; повторное открытие завершённой попытки не вызывает новую генерацию.
Незавершённый внешний вызов требует явного восстановления по правилам сервиса.
Остановка, лимит времени и инфраструктурная ошибка не направляются обратно
модели как математическая обратная связь.

Выбор движка фиксируется в контракте как `proof_backend: "native"` или
`"goedel-adapted"`. Модель остаётся `gpt-6-astra`. Метаданные и происхождение
доступны через `backend_metadata()` и сохраняются в результате исследования.

## Проверка без модели

Из каталога приложения, с настроенным `ATLAS_LEAN`:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p test_research_goedel.py -v
.\.venv\Scripts\python.exe -X utf8 tools/goedel/verify_adapter.py --output ../../runs/current/goedel-compatibility
```

`verify_adapter.py` повторяет доступное решение существующего `graph_energy`,
использует настоящий upstream graft и реально запускает Lean для двух узлов
и финальной композиции. Любая попытка вызвать модель завершает проверку ошибкой.
Это проверка совместимости с известным решением, не слепое переоткрытие.
Отчёт сохраняет команды Lean, хеши, аксиомы и результаты; смысловая рецензия и
научная новизна этим запуском не устанавливаются.

`--output` задаёт каталог JSON-отчёта. Lean-файлы и промежуточные модули по
умолчанию находятся в `apps/msc-lean-atlas/verification/goedel-compatibility/`,
даже если отчёт сохраняется в корневом `runs/current/`. Параметр `--work-dir`
позволяет явно выбрать другой рабочий каталог. В корневой комплект 11/149
дополнительные Lean-файлы не добавляются.

## Сравнение движков

Фиксированный протокол: `tools/goedel/backend-benchmark.json`. Включены известная
положительная связь и два отрицательных контроля. Пометка `heldout_protocol`
означает исключение из настройки адаптера, не отсутствие этих задач в обучении
модели. Решения доступны в репозитории; это явно указано в отчёте.

Без `--live` команда только показывает протокол и не вызывает модель:

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/goedel/evaluate_backends.py
.\.venv\Scripts\python.exe -X utf8 tools/goedel/evaluate_backends.py --report verification/backend-evaluation.json
```

Явный живой эксперимент вызывает модель и расходует аккаунтный бюджет:

```powershell
.\.venv\Scripts\python.exe -X utf8 tools/goedel/evaluate_backends.py --live --output verification/backend-evaluation.json
```

Для каждой задачи сохраняются обе попытки с одинаковыми режимом, моделью и
верхними пределами времени/вызовов. Отчёт проверяет точные входы и окружения,
учитывает **все** вызовы, фактические токены, время и причины остановки.
Рабочие файлы сохраняются в `apps/msc-lean-atlas/verification/backend-runs/`;
расположение JSON-отчёта не меняет этот каталог. `--work-dir` переопределяет его явно.
Seed API не предоставляет; значение не придумывается. Полный успех требует
всех Lean-обязательств и согласованной смысловой рецензии. Малый набор не
обосновывает превосходство архитектуры; сравнение остаётся измерением именно
этих запусков.
