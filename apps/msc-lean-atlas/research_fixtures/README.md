# Проверяемые задачи исследовательского этапа

Здесь находятся фиксированные контрольные задачи и эталонные доказательства.
`research_lean.fixtures()` передаёт агентам **только определения, постановку и
граф обязательств**, без текстов эталонных доказательств. Это контроль
восстановления известных результатов, а не доказательство новизны.

## Происхождение и границы

- `SeminarOriginal.lean` — неизменённый `hw_sol.lean` Ивана Фомина из публичных
  материалов «Основы языка Lean», 27.10.2026:
  <https://disk.360.yandex.ru/d/U4LZDftMoV55kg>.
- `SeminarGradient.lean` — производная копия для доступного Lean 4.19.0.
  Единственная правка доказательства: `field_simp` → `field_simp; ring` в
  `one_step`. Исходные определения, предпосылки и выводы сохранены. Оригинал
  на этом окружении оставляет коммутативное кольцевое равенство незакрытым.
- `StrictCounterexample.lean` — доказательство отрицания универсального
  строгого неравенства `2ab < a²+b²`, встречающегося как незавершённый учебный
  пример в `sem.lean`. Свидетель `a=b=0`. Успех этого файла означает
  **опровержение исходной гипотезы**, а не её доказательство.
- `GraphEnergy.lean` — явная координатная модель взвешенного треугольника:
  энергия рёбер равна квадратичной форме лапласиана; неотрицательность
  переносится через равенство. Это известное тождество на конкретном классе
  графов, не новый результат и не доказательство для всех графов.

## Что проверяет модуль

1. Исходник компилируется заново в отдельной папке.
2. Декларации, их типы и зависимости экспортируются из Lean environment.
3. Все локальные декларации и транзитивные аксиомы цели проходят аудит.
   Допускаются только стандартные `propext`, `Classical.choice`, `Quot.sound`.
4. Отдельный `Contract.lean` проверяет, что значение целевой теоремы имеет
   заданный извне тип. Проверка типа не допускает незаметного добавления
   предположений либо ослабления вывода.
5. Итоговая композиция проверяется целиком; отображаемые рёбра взяты из
   скомпилированной программы, а не только из предварительного плана.

Контроллер обязан сохранять исходный `prelude`: одинаковые имена изменённых
определений не означают одинаковую математическую постановку. Проверка смысла,
полезности и новизны остаётся отдельной от Lean. `xstar : E` в `gd_rate` не
содержит предположения минимальности.

Версии Lean, ревизии библиотек, хеши исходников и журнал каждой проверки
сохраняются в `verification.json`. Используются установленные внешние
`.olean`-кэши; полная пересборка mathlib не выполняется.

Проверка принимает ограниченное подмножество исходников и запрещает явные
compile-time команды, метапрограммирование и дополнительные аксиомы. Это
консервативная проверка локальных кандидатов, **не общий sandbox исполнения
произвольного Lean-кода из интернета**.

`verification/` содержит фактические проверки разработки, включая неудачные
попытки. Актуальный статус следует брать из конкретного результата запуска,
а не из самого наличия эталонного `.lean` файла.
